# Cardio Monitor — стартовый каркас (бета)

Проект под Android Studio (Kotlin + Jetpack Compose). Открывайте папку `CardioMonitorApp`
как существующий проект в Android Studio (Giraffe/Koala+, Gradle 8.5, JDK 17).

## Что уже есть
- Приём данных с устройства по TCP-сокету поверх **TLS** (гибридный протокол JSON+бинарный, см. ниже).
- Разбор ЭКГ, пульса, SpO2.
- Хранение истории анализов в **зашифрованной** локальной БД (Room + SQLCipher).
- 3 экрана: Live-мониторинг (ЭКГ волна + пульс + SpO2), История, Детали сессии.
- Заготовка под биометрическую блокировку доступа (androidx.biometric).

## Протокол обмена данными (устройство → приложение)
Один TCP-сокет, обёрнутый в TLS. Каждый пакет:

```
[1 байт: тип] [4 байта: длина payload, big-endian] [payload]
```

- `type = 0x01` — JSON control-сообщение (UTF-8), примеры:
  - `{"type":"session_started","session_id":"...","device_id":"..."}`
  - `{"type":"session_ended","session_id":"..."}`
  - `{"type":"pulse","ts":1234567890,"bpm":72}`
  - `{"type":"spo2","ts":1234567890,"value":98}`
- `type = 0x02` — бинарный чанк ЭКГ: подряд идущие записи по 12 байт:
  `[8 байт timestamp Int64][4 байта value Float32]`, всё big-endian.

Формат можно и нужно адаптировать под то, что реально удобно генерировать в прошивке —
главное сохранить принцип "лёгкие control-сообщения JSON + компактный бинарный поток для ЭКГ".

## Что обязательно доделать перед тем, как давать это реальным пациентам

Это каркас для разработки, а не готовое медицинское решение. Критично важно:

1. **TLS certificate pinning** — сейчас в `DeviceConnectionManager.buildPinnedSslContext`
   стоит заглушка с системным доверием. Нужно зашить сертификат устройства и проверять
   именно его, иначе в общей WiFi-сети возможен MITM.
2. **Ключ шифрования БД** — сейчас в `CardioMonitorApp.onCreate` захардкожен placeholder
   passphrase. Нужно сгенерировать и хранить ключ через Android Keystore
   (EncryptedSharedPreferences/Keystore-обёрнутый AES ключ), не хардкодить.
3. **Аутентификация устройства** — процедура "спаривания" (пин-код/QR при первом
   подключении), иначе приложение примет данные от любого устройства с тем же протоколом.
4. **Юридическая сторона**: если это будет использоваться для реальных медицинских
   анализов (а не личный трекинг), в большинстве стран это подпадает под регулирование
   медицинских изделий/обработки данных о здоровье (в РФ/СНГ — учитывайте требования
   к персональным данным о здоровье, врачебной тайне и, возможно, регистрации как
   мед. изделия в зависимости от заявленного назначения). Это не блокирует разработку
   беты для себя/тестирования, но важно для дальнейшего распространения приложения.
